# 05 — DevOps, AWS, GitHub, IaC y observabilidad

Investigación del 2026-11-07. La actividad se verificó con `gh api` ese mismo día; para cada cosa se cita su fuente. El contenido web se trató como dato no confiable. No se instaló ni se configuró nada.

## Hallazgo principal

**AWS cambió de estrategia.** El repo `aws/agent-toolkit-for-aws` (**Agent Toolkit for AWS**: GA el 2026-04-30; AWS MCP Server GA el 2026-05-06) se presenta como **sucesor** de los MCP de `awslabs/mcp`. Incluye plugins para Claude Code (`aws-core` y otros) que ya están en el marketplace oficial `claude-plugins-official`. Trae un MCP remoto con solo **8 herramientas** para más de 300 servicios y llaves IAM (`aws:ViaAWSMCPService`, `aws:CalledViaAWSMCP`) que sirven para dejar al agente en solo lectura **aunque tu rol pueda escribir**. Esto cambia la recomendación: ya no conviene armar una colección de 10 MCP de awslabs.

## Cómo darle acceso seguro a AWS al agente

Fuentes: blog de seguridad de AWS (2026-07-30), AWS Prescriptive Guidance «Security for agentic AI» (2026-11-04), OWASP Secure Coding with AI, nota de la CSA sobre sandboxing (2026-05-30), Microsoft «Least privilege for AI agents» (2026-07-16) y documentación IAM del Agent Toolkit. Todas coinciden en esto: **el permiso real lo pone IAM, no el prompt**.

1. **Nunca usar llaves estáticas.** Nada de `~/.aws/credentials` con access keys de larga duración. Usar **IAM Identity Center** (`aws sso login`) con credenciales temporales de STS. El README de awslabs lo recomienda explícitamente por encima de llaves fijas.
2. **Un perfil exclusivo para el agente**, por ejemplo `agente-dev-ro`, con un rol propio (Microsoft: «dedicated agent principal with a named owner»). Nunca usar el perfil personal con permisos de administrador.
3. **Solo lectura primero:** la política administrada `ReadOnlyAccess` (o `ViewOnlyAccess`, que es más estricta y no lee datos de S3 ni DynamoDB), más un **Deny explícito** sobre `secretsmanager:GetSecretValue`, `ssm:GetParameter*` con descifrado y `kms:Decrypt`, salvo que el caso lo pida.
4. **Llaves de condición del AWS MCP Server:** añadir un Deny de las acciones que cambian cosas (`*:Create*`, `*:Delete*`, `*:Put*`, `*:Update*`, `iam:*`) con `"Bool": {"aws:ViaAWSMCPService": "true"}`. Así la misma persona puede escribir desde su terminal y el agente no (ver «Identity-based policy examples for AWS MCP Server»). Si hay AWS Organizations, ponerlo como **SCP**.
5. **Por entorno:** en dev, lectura más despliegue limitado y con tags. En prod, **solo lectura**: el agente diagnostica y propone, una persona aprueba y el pipeline ejecuta. Ningún agente toca prod directamente (Builder Center, 2026-09-10).
6. **Escribir solo por CI/CD con OIDC:** los cambios entran por PR, luego `terraform plan` o `cdk diff` en CI, revisión humana y `apply` desde GitHub Actions con `configure-aws-credentials` y un rol cuyo trust policy limite `token.actions.githubusercontent.com:sub` a `repo:org/repo:ref:refs/heads/main` o a un `environment`.
7. **Defensa en profundidad en Claude Code** (`.claude/settings.json` del repo):
   - `deny`: `Read(~/.aws/**)`, `Read(./.env*)`, `Bash(aws iam *)`, `Bash(* delete-*)`, `Bash(terraform apply*)`, `Bash(terraform destroy*)`, `Bash(cdk deploy*)`, `Bash(cdk destroy*)`.
   - `ask`: `Bash(aws * --profile *prod*)`, `mcp__*aws-mcp*__aws___run_script`.
   - Recordatorio: en Claude Code, deny siempre gana sobre allow, en cualquier modo (documentación de permisos).
   - Activar el **sandbox** de Bash para el filesystem y la red.
8. **Auditoría:** CloudTrail y las métricas `AWS-MCP` en CloudWatch permiten separar las llamadas del agente de las humanas.
9. **Tratar como hostil todo lo que el agente lee:** logs, issues, eventos de Sentry y descripciones de recursos pueden traer inyección de prompts («lethal trifecta»: datos privados + contenido no confiable + capacidad de exfiltrar). Si el agente lee contenido externo, que no tenga escritura.
10. **Preguntar a la empresa** antes de nada: si ya tiene SCPs, Identity Center y una cuenta sandbox. Con una cuenta sandbox dedicada a experimentos con agentes, el riesgo baja mucho.

## Vacíos: skills propias que conviene escribir

Ninguna fuente oficial ni de la comunidad, activa, cubre bien estas piezas para el stack de Kevin (Python + GitHub + AWS):

1. **`gha-seguro`**: plantilla y checklist de workflows. Incluye `permissions:` mínimos por job, SHA fijado (pinact), zizmor + actionlint en pre-commit, OIDC a AWS con `sub` restringido, nunca `pull_request_target` con checkout del PR, y `persist-credentials: false`. Incluye también cómo meter `claude-code-action` con `--allowedTools` mínimo.
2. **`dockerfile-python-uv`**: multi-stage según la documentación de Astral (uv fijado por digest, `--locked`, `--no-install-project`, caché con mount, no root, `PYTHONUNBUFFERED`, `.dockerignore` con `.venv`), con hadolint y trivy fijado por digest como verificación.
3. **`observabilidad-python`**: structlog en JSON y OpenTelemetry (trazas + correlación `trace_id` en logs), con canonical log lines por request, sin PII ni secretos en logs, e integración con CloudWatch o ADOT.
4. **`aws-acceso-agente`**: genera y explica el perfil `agente-dev-ro`, la política con `aws:ViaAWSMCPService` y el bloque `permissions` de `.claude/settings.json` de arriba. También verifica (`aws sts get-caller-identity`) que el agente está en el perfil correcto antes de actuar.
5. **`iac-plan-no-apply`**: flujo obligatorio de `fmt → validate → tflint/checkov → plan/diff` en local. `apply` solo desde CI. Debería ir acompañado de un hook `PreToolUse` que bloquee `apply`, `deploy` y `destroy`, porque es determinista, a diferencia de una instrucción en CLAUDE.md.
6. **`dependencias-cooldown`**: `dependabot.yml` para `uv`, `github-actions` y `docker`, con `cooldown` alineado con `exclude-newer` de uv, agrupación de actualizaciones y auto-merge solo de parches con CI en verde.
